◆ vigil

A Rust terminal monitor for people who run servers and debug networks, on Linux, macOS and Windows. Processes, sockets and open files live in one screen, with lsof built in, and a doctor walks the network layer by layer. This handbook shows how it works and how to solve the usual incidents with it.

Overview on a fictional web server. Everything you want to know first during an incident is on one screen: CPU, memory, traffic, which ports are open and how the TCP connections are doing.

How it works

vigil collects data on three background threads. The main thread does nothing but handle keys and draw. That keeps the interface responsive, even when lsof needs a few seconds on a busy server.

On Linux, vigil reads sockets straight from /proc/net/tcp* and /proc/net/udp*. That is much faster than lsof -i and also shows TIME_WAIT, which lsof misses because those sockets no longer have an owner. To use lsof anyway, start with --lsof-sockets. macOS always uses lsof.

Playbooks

Common incidents, each with the symptom, the keys you press and why it works. Everywhere: y copies the selected value, E exports the table to CSV, and you can click tabs, rows and column headers.

After a security update

You ran apt upgrade; the NEEDS RESTART badge is on.

  1. The badge counts processes still running a replaced binary or library (for example the old libssl.so.3).
  2. 2, select one, ↵: the inspector says what was replaced and which unit owns it.
  3. systemctl restart that unit; the badge drops within two minutes.

A patched library on disk does nothing for a process that loaded the old one. Until it restarts, it is still vulnerable.

A slow leak

A service gets slower over the day.

  1. 2, select it, ↵ for the inspector.
  2. Watch the memory and open-fd graphs: a trend like +38 % in 2 min under steady load is a leak.
  3. v shows its environment; the journal shows what it was doing.

A single number never shows a leak. A line that only goes up does.

What did my deploy change?

Something feels different after a release.

  1. Before: vigil report -f json -o before.json
  2. Deploy.
  3. After: vigil report --diff before.json

The diff lists new findings, ports that opened or closed, services that failed or recovered, containers that came or went, and memory, disk and connection shifts. Paste it into the change ticket.

"Too many open files"

A service starts refusing connections; the FDS badge is on.

  1. 2 e sorts processes by open file descriptors.
  2. The detail pane shows open/limit (%) for the selected process.
  3. ↵ lists its descriptors: thousands of the same socket or file means a leak.

Fix the leak, or raise LimitNOFILE in the unit. A count that only grows over time is a leak; raising the limit just delays the outage.

Disk full, but there is space

Writes fail with "No space left on device" while df -h shows free GB.

  1. 6 and look at the INODES column, or the INODES badge.
  2. At 100 % no new file can be created, whatever the free space.
  3. Find the directory with millions of small files (sessions, caches, mail queues).

Every file needs an inode, and ext4 fixes their number at mkfs time. Deleting small files is the only quick fix.

Slow pod, idle node

A container is slow while the host has spare CPU.

  1. 0 Containers and look at THROTTLED.
  2. A high share means it hits its CPU quota (cpu.max) every period.
  3. Compare CPU% with the LIMIT column.

CFS throttling pauses all threads of the container until the next period, which shows up as latency spikes. Raise the limit or drop it and rely on requests.

Something got killed

A process disappeared; the OOM badge is on.

  1. S System, e to the kernel events: the OOM line names the victim and its memory use.
  2. In a container: 0 shows the OOM count and memory against its limit.
  3. e back to the units and its journal shows what it was doing.

The OOM killer only logs to the kernel ring buffer. Without dmesg you just see a process that is gone.

"Address already in use"

Your deploy fails because port 8080 is taken.

  1. : :8080 ↵
  2. Read the PID and COMMAND. Often it's an old instance that never exited.
  3. x → SIGTERM, and only if that doesn't work, SIGKILL.

TERM first, so the process can still shut down cleanly. KILL can't be caught, so nothing gets flushed or cleaned up.

Disk full, but du finds nothing

df says 100 %, but du comes up tens of GB short.

  1. : +L1 ↵ lists deleted files that are still open.
  2. Look at SIZE/OFF. It's usually a rotated log that is still held open.
  3. Select the process and send SIGHUP so it reopens its logs.

A file deleted while a process still has it open keeps using space. The space only comes back when the last fd closes.

Reload a config without downtime

You changed the nginx or haproxy config.

  1. 2 / nginx ↵, t for the tree
  2. Select the master process, the top one in the tree.
  3. x → SIGHUP

The tree view shows at a glance which process is the master and which are workers. Send HUP to the master only.

Track down a memory leak

Swap slowly fills up.

  1. 2 m sorts by memory.
  2. Let it run for a few minutes. The selected process stays selected even when the order shifts.
  3. Compare RSS and virt in the detail pane.

If RSS keeps growing while traffic stays flat, you probably have a leak. If only virt grows, there's usually nothing wrong.

Who is writing to this file?

A log or database file grows fast.

  1. : /var/log/app/out.log ↵
  2. The FD column shows w or u for processes that write.
  3. 6 shows how much each process is writing right now.

lsof tells you who has the file open, the Storage view tells you how much. Together you know who's responsible.

Zombies and orphans

The process count keeps rising.

  1. 2 t turns on the tree view.
  2. Look for Z in the ST column.
  3. Signal the parent, not the zombie itself.

A zombie is already dead and ignores every signal. It only goes away when the parent calls wait() or exits.

Which container is this?

An unknown process is burning CPU.

  1. Select it and check exe and cmd in the detail pane.
  2. ↵ shows its open files. Paths under /var/lib/docker/overlay2 or containerd give a container away.
  3. Is the parent containerd-shim? The tree shows it.

Until there's a container view, this is the fastest way to tie a process to a container.

What runs under this user?

You're auditing a service account.

  1. : -u www-data ↵ shows everything that user has open.
  2. / IPv narrows that to network only.

Anything starting with - or + goes to lsof unchanged, so every lsof option is available.

Who is on the box?

Unexpected load, or a security question.

  1. U: logged-in sessions with source address and what they run. Public addresses are highlighted.
  2. Below: failed SSH logins in the last hour per source and the usernames tried.
  3. y copies an address for your firewall or fail2ban.

Hundreds of attempts from one address with users like root, admin and test is a password-guessing bot. Make sure password login is off.

Where on the path is the loss?

A probe shows loss or jitter to an external target.

  1. 8, select the probe, press t.
  2. The path appears hop by hop with loss and latency (mtr, or traceroute).
  3. Loss that starts at one hop and continues to the end is real; loss at a single middle hop is usually ICMP rate limiting.

This separates your network, your provider and the far end in one look.

Certificate about to expire

You want to know before the browser does.

  1. 8 a https://api.example.com/health
  2. The CERT column shows the days left; the CERT badge appears under 21 days.
  3. STATUS shows the HTTP code, LAST ms the time to first byte.

An expired certificate is one of the most common avoidable outages. Probes are saved, so this check runs every time vigil is open.

Packet loss on the path

Users report slowness; the RETRANS badge is on.

  1. 4 s until you sort by rtt; the slow and retransmitting connections float to the top.
  2. Do they share one remote network? Check 8 Probes for loss to the gateway versus external targets.
  3. C on a bad connection records 20 s of it for Wireshark.

Loss to the gateway is local (cable, switch, Wi-Fi). Loss only beyond it is the uplink or the provider. The capture shows retransmissions and dup-ACKs as proof.

Listen queue overflow

Clients time out while the service looks idle; the LISTEN DROPS badge is on.

  1. 4 l: listening sockets with a non-zero RECV Q are full.
  2. Compare the queue with the backlog the service configures.
  3. Raise the backlog and net.core.somaxconn, or add workers.

When the accept queue is full the kernel silently drops SYNs. Nothing is logged by the application, so this is easy to miss without the counter.

TIME_WAIT storm

Outgoing connections sometimes fail with EADDRNOTAVAIL.

  1. 4 and check the TIME_WAIT chip at the top. Past the threshold it also shows as a header badge.
  2. Press s until you sort by remote to see which upstream it is.
  3. Tens of thousands to one backend means there's no keep-alive or connection pooling.

Every short-lived connection holds an ephemeral port for 60 s after closing. Use pooling or keep-alive, or widen ip_local_port_range.

CLOSE_WAIT leak

The CLOSE_WAIT count climbs and never comes down.

  1. 4 / close_wait
  2. Read the PROCESS column. It's usually the same application every time.
  3. ↵ shows all its fds. Does that number keep growing?

CLOSE_WAIT means the other side closed the connection, but your application never closes the socket. That's always a bug in the app, not in the network.

Stuck in SYN_SENT

Connections to one host hang.

  1. 4 / syn_sent
  2. Read the remote IP and port.
  3. Stays in SYN_SENT? Then no SYN-ACK is coming back.

A firewall silently dropping packets, wrong routing or a security group. A RST fails fast; a DROP leaves the connection hanging.

Exposure audit

What can be reached from outside?

  1. 4 l shows listening sockets only.
  2. *:5432 listens on every interface, 127.0.0.1:5432 only locally.
  3. P on a row shows everything using that port.

A database or Redis listening on * is a common leak. Check after every deploy.

Interface errors

Packet loss or a slow link.

  1. 3 and check the ERR column. It turns red as soon as it's above 0.
  2. Select the interface and look at the graph for spikes or a ceiling.
  3. A flat ceiling in the graph means the link is saturated.

Rising rx errors point at layer 1 or 2: a bad cable, a duplex mismatch or a driver problem. You can't fix that in the application.

Who talks to whom?

You want to know which hosts a server talks to.

  1. 3 and check the top peers list on the right.
  2. An unknown IP? 4 / and paste the IP.
  3. Now you see which process and user own the connection.

This also finds forgotten cron jobs and connections to old endpoints. During a security incident it's often the first step.

IPv4 or IPv6?

A service is reachable over IPv4 but not over IPv6.

  1. 4 l and check the PROTO column: TCP v4 or TCP v6.
  2. No v6 listener means the service doesn't bind to [::].

On Linux a socket on [::] accepts IPv4 too, unless bindv6only is set. A service bound only to 0.0.0.0 can't be reached over IPv6.

UDP services

DNS, syslog or WireGuard isn't working.

  1. : udp:53 ↵ (or udp:514, udp:51820)
  2. See which process owns the port. For DNS that's often systemd-resolved on 127.0.0.53.

UDP has no states. A socket without a remote address is simply waiting for packets, and vigil shows it as listening.

Themes

Press T for the theme picker. ↑ ↓ previews live, ↵ keeps it, Esc goes back, and b switches between the theme's background and your terminal's own. Your choice is saved to the config file when you quit.

Two themes change the characters as well as the colours. cyberpunk draws thick neon frames and ▰▱ meters. phosphor turns vigil into a green P1 CRT: pure 7-bit ASCII (+--+, ###..., |- trees), monochrome green, and severity shown only by brightness, like a VT100.

ansi uses your terminal's 16 colours instead of fixed RGB values. Use it over plain SSH, in tmux without truecolor or on a serial console. With theme = "auto", vigil picks it by itself when the terminal doesn't support truecolor.

Reports

vigil report samples the system for one second and prints a Markdown report: health, system info, CPU and load, memory, PSI, top processes by CPU and memory, listening ports with an exposed flag, connection states, top peers, interfaces, filesystems and temperatures. Inside the TUI, R writes the same report to ./vigil-report-<time>.md.

CommandUse

vigil report --fail-on-alertExits with code 2 when a health threshold is crossed, for cron and CI
