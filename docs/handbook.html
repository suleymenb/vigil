◆ vigil

A Rust terminal monitor for people who run servers and debug networks. Processes, sockets and open files live in one screen, with lsof built in. This handbook shows how it works and how to solve the usual incidents with it.

Overview on a fictional web server. Everything you want to know first during an incident is on one screen: CPU, memory, traffic, which ports are open and how the TCP connections are doing.

How it works

vigil collects data on three background threads. The main thread does nothing but handle keys and draw. That keeps the interface responsive, even when lsof needs a few seconds on a busy server.

On Linux, vigil reads sockets straight from /proc/net/tcp* and /proc/net/udp*. That is much faster than lsof -i and also shows TIME_WAIT, which lsof misses because those sockets no longer have an owner. To use lsof anyway, start with --lsof-sockets. macOS always uses lsof.

The six views

1 · Overview

The whole system on one screen

Start here for every incident.
2 · Processes

Sort, tree and signals

CPU, memory, disk I/O per second and the number of sockets per process. A detail pane at the bottom shows ppid, exe and the full command line.

3 · Network

Interfaces and peers

Per interface: rates, totals, packets, errors, MAC and addresses. A graph for the selected interface and the remote hosts with the most connections.

4 · Sockets

Every connection with its owner

Proto, local, remote, colour-coded state, pid, process, user and fd. The top bar counts sockets per state.

5 · Open Files

lsof on demand

By pid, port, path or with raw arguments. The top bar counts files per type (REG, IPv4, PIPE, unix …).

6 · Storage

Disks, I/O and temperatures

Usage per filesystem, which processes are reading or writing right now, and sensors with their critical limits.

Sensors refresh every 2 s on this view.

Health badges

The right side of the tab row shows a badge for every threshold that is crossed, on every view. When all is well it reads ✓ healthy. You set the thresholds in the [alerts] section of the config file; 0 turns a check off.

Playbooks

Common incidents, each with the symptom, the keys you press and why it works.

"Address already in use"

Your deploy fails because port 8080 is taken.

  1. : :8080 ↵
  2. Read the PID and COMMAND. Often it's an old instance that never exited.
  3. x → SIGTERM, and only if that doesn't work, SIGKILL.

TERM first, so the process can still shut down cleanly. KILL can't be caught, so nothing gets flushed or cleaned up.

Disk full, but du finds nothing

df says 100 %, but du comes up tens of GB short.

  1. : +L1 ↵ lists deleted files that are still open.
  2. Look at SIZE/OFF. It's usually a rotated log that is still held open.
  3. Select the process and send SIGHUP so it reopens its logs.

A file deleted while a process still has it open keeps using space. The space only comes back when the last fd closes.

Reload a config without downtime

You changed the nginx or haproxy config.

  1. 2 / nginx ↵, t for the tree
  2. Select the master process, the top one in the tree.
  3. x → SIGHUP

The tree view shows at a glance which process is the master and which are workers. Send HUP to the master only.

Track down a memory leak

Swap slowly fills up.

  1. 2 m sorts by memory.
  2. Let it run for a few minutes. The selected process stays selected even when the order shifts.
  3. Compare RSS and virt in the detail pane.

If RSS keeps growing while traffic stays flat, you probably have a leak. If only virt grows, there's usually nothing wrong.

Who is writing to this file?

A log or database file grows fast.

  1. : /var/log/app/out.log ↵
  2. The FD column shows w or u for processes that write.
  3. 6 shows how much each process is writing right now.

lsof tells you who has the file open, the Storage view tells you how much. Together you know who's responsible.

Zombies and orphans

The process count keeps rising.

  1. 2 t turns on the tree view.
  2. Look for Z in the ST column.
  3. Signal the parent, not the zombie itself.

A zombie is already dead and ignores every signal. It only goes away when the parent calls wait() or exits.

Which container is this?

An unknown process is burning CPU.

  1. Select it and check exe and cmd in the detail pane.
  2. ↵ shows its open files. Paths under /var/lib/docker/overlay2 or containerd give a container away.
  3. Is the parent containerd-shim? The tree shows it.

Until there's a container view, this is the fastest way to tie a process to a container.

What runs under this user?

You're auditing a service account.

  1. : -u www-data ↵ shows everything that user has open.
  2. / IPv narrows that to network only.

Anything starting with - or + goes to lsof unchanged, so every lsof option is available.

TIME_WAIT storm

Outgoing connections sometimes fail with EADDRNOTAVAIL.

  1. 4 and check the TIME_WAIT chip at the top. Past the threshold it also shows as a header badge.
  2. Press s until you sort by remote to see which upstream it is.
  3. Tens of thousands to one backend means there's no keep-alive or connection pooling.

Every short-lived connection holds an ephemeral port for 60 s after closing. Use pooling or keep-alive, or widen ip_local_port_range.

CLOSE_WAIT leak

The CLOSE_WAIT count climbs and never comes down.

  1. 4 / close_wait
  2. Read the PROCESS column. It's usually the same application every time.
  3. ↵ shows all its fds. Does that number keep growing?

CLOSE_WAIT means the other side closed the connection, but your application never closes the socket. That's always a bug in the app, not in the network.

Stuck in SYN_SENT

Connections to one host hang.

  1. 4 / syn_sent
  2. Read the remote IP and port.
  3. Stays in SYN_SENT? Then no SYN-ACK is coming back.

A firewall silently dropping packets, wrong routing or a security group. A RST fails fast; a DROP leaves the connection hanging.

Exposure audit

What can be reached from outside?

  1. 4 l shows listening sockets only.
  2. *:5432 listens on every interface, 127.0.0.1:5432 only locally.
  3. P on a row shows everything using that port.

A database or Redis listening on * is a common leak. Check after every deploy.

Interface errors

Packet loss or a slow link.

  1. 3 and check the ERR column. It turns red as soon as it's above 0.
  2. Select the interface and look at the graph for spikes or a ceiling.
  3. A flat ceiling in the graph means the link is saturated.

Rising rx errors point at layer 1 or 2: a bad cable, a duplex mismatch or a driver problem. You can't fix that in the application.

Who talks to whom?

You want to know which hosts a server talks to.

  1. 3 and check the top peers list on the right.
  2. An unknown IP? 4 / and paste the IP.
  3. Now you see which process and user own the connection.

This also finds forgotten cron jobs and connections to old endpoints. During a security incident it's often the first step.

IPv4 or IPv6?

A service is reachable over IPv4 but not over IPv6.

  1. 4 l and check the PROTO column: TCP v4 or TCP v6.
  2. No v6 listener means the service doesn't bind to [::].

On Linux a socket on [::] accepts IPv4 too, unless bindv6only is set. A service bound only to 0.0.0.0 can't be reached over IPv6.

UDP services

DNS, syslog or WireGuard isn't working.

  1. : udp:53 ↵ (or udp:514, udp:51820)
  2. See which process owns the port. For DNS that's often systemd-resolved on 127.0.0.53.

UDP has no states. A socket without a remote address is simply waiting for packets, and vigil shows it as listening.

Themes

Press T for the theme picker. ↑ ↓ previews live, ↵ keeps it, Esc goes back, and b switches between the theme's background and your terminal's own. Your choice is saved to the config file when you quit.

ansi uses your terminal's 16 colours instead of fixed RGB values. Use it over plain SSH, in tmux without truecolor or on a serial console. With theme = "auto", vigil picks it by itself when the terminal doesn't support truecolor.

Configuration

Settings live in ~/.config/vigil/config.toml, on macOS too. Command-line flags win over the file, and the file wins over the defaults. A broken file never stops vigil: it starts with defaults and shows a warning in the footer.

Roadmap

What I'd add next to keep vigil useful for years, in order of priority. Themes, the config file and health badges shipped in v0.2.

Next

Containers: Docker, Podman and cgroups

A view with CPU, memory and network per container, read from cgroup v2 (/sys/fs/cgroup), so without the Docker daemon. On modern servers almost everything runs in a container.

Next

Linux: netlink sock_diag instead of /proc/net

This adds RTT, retransmits, cwnd and the send/receive queue per socket, like ss -ti. For a network engineer that's gold: you see a slow connection before users complain.

Then

Bandwidth per process

Through eBPF on Linux or nettop on macOS. Then you don't just know that 40 MB/s is crossing the link, but also which process is sending it.

Then

systemd units and the journal

Status, restarts and the last log lines per unit. Selecting a unit and seeing journalctl -u right away saves you a terminal window.

Then

Alert hooks

A webhook or command that runs when a health badge appears, so vigil can page you while you look at something else.

Later

Record and replay

Write snapshots to JSON and replay them later or on another machine. Handy for a post-mortem: what was going on at 03:12?

Later

Async reverse DNS and latency targets

Show IPs as host names without freezing the interface. Plus a small ping and TCP-connect monitor for targets you configure yourself.

Later

Custom themes in the config file

Define your own palette in config.toml instead of picking one of the built-in themes.
